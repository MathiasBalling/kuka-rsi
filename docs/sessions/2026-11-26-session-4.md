# Session 4: pause and resume, session end reasons (2026-11-26)

Same cell as sessions 1 to 3, T1, override 100 % unless noted. Plan: S6.5 from
[session 2](2026-11-05-session-2.md) (the pause by Start key and enabling switch, the
override), which issue #1 asks for, and the end reason of a session for every way it can end.
The moves are `jog --axis 6 --deg 30 --repeat 1` (out and back) with 10 s or 30 s legs; the
end reasons come from `runs/end.py`, a script around `Driver(stop_channel="MoveStop")` that
ends the session in one way per run and prints `last_session_end()` and the events.

The driver changed during the session. Runs 1 to 4 used commit `7457515`. The pauses ended
RSI there, so the fix was written at the robot and the later runs used it; it is commit
`728f5a8`.

## What the robot does when its program stops

From the logs of the first three runs (`s6_5_1.csv`, `s6_5_2.csv`, `s6_5_3.csv`), the same in
every later run:

- **The telegrams continue.** No telegram is missing through any pause, with the Start key
  released (2.4 to 4.1 s) or the enabling switch (5.7 to 126 s). The session stays `Active`
  and `program_running` reads 0.
- **The stop is reported late.** The robot is below half its speed 8 to 9 cycles before
  `program_running` turns 0 (nine stops). With the following lag on top, the command is
  ahead of the standing robot by about 65 ms of motion: 0.10° at 1.5 °/s, 0.32° at 4.8 °/s.
- **A stopped robot ignores the correction.** With the Start key released the drives stay
  on and the robot holds its place against an offset of 0.2 to 0.3° for seconds, drifting
  up to 0.014°. With the enabling switch released all six motor torques read exactly 0
  from about 0.2 s after the stop: the drives are off.
- **It takes the whole offset at once when it moves again.** A6 jumped at 14 °/s for 40 ms
  across 0.21° (the move was doing 3 °/s) and went on. Across 0.29° and 0.35° RSI ended
  instead, with a "command velocity A6" message on the pendant (text as reported, number
  not noted).
- **After the enabling switch, `ProgStatus` is early.** It reads "running" 56 to 64 ms
  before the first motor torque is back and 116 to 124 ms before A2's is (four resumes).
  The old driver played the move during that time, so the offset grew from 0.12° to 0.35°
  and RSI ended the moment the drives were on.
- **The override works as designed.** `OvPro` follows the pendant in its steps
  (10 → 30 → 50 % and back), the robot tracks the scaled playback within 0.09°, and
  nothing is clamped.

With only the enabling switch released and Start still held, the pendant asks to confirm a
message about RSI not being able to set outputs because of operator protection (text as
reported). After the confirmation the move went on.

## The fix

`728f5a8`, see `docs/design.md` §15 for the mechanism. While `ProgStatus` is not 3, and for
0.5 s after it is again, the command is the measured position and nothing is played. At the
stop the move is taken back to the point of the path where the robot came to stand. After
the wait the playback returns to full speed over 0.5 s.

| Run | Driver | Pause | Offset at the resume | Robot's peak speed after the resume | Move's speed there | Outcome |
| --- | --- | --- | --- | --- | --- | --- |
| `s6_5_1.csv` | `7457515` | Start key, 2.5 s | 0.21° | 14.4 °/s | 3 °/s | went on |
| `s6_5_1.csv` | `7457515` | Start key, 2.4 s | 0.29° | | 4 °/s | RSI ended 5 cycles after Start, "command velocity A6" |
| `s6_5_2.csv` | `7457515` | Start key, 3.4 s | 0.11° | 7.2 °/s | 1.6 °/s | went on |
| `s6_5_3.csv` | `7457515` | enabling switch, 41 s | 0.12°, then 0.35° | | 1.8 °/s | RSI ended 124 ms after "running" |
| `s6_5_1_fix.csv` | follow and wait | Start key, 3.5 s | 0 | 11.1 °/s | 5 °/s | went on; the command made up 0.32° at the 10 °/s limit |
| `s6_5_3_fix.csv` | follow and wait | enabling switch, 126 s | 0 | 7.8 °/s | 1.6 °/s | went on |
| `s6_5_3_fix.csv` | follow and wait | enabling switch, 55 s | 0 | 2.6 °/s | 0.6 °/s | went on |
| `s6_5_rewind.csv` | `728f5a8` | Start key, 4.1 s | 0 | 6.0 °/s | 4.6 °/s, peak 5.9 | went on |
| `s6_5_rewind.csv` | `728f5a8` | both released, 5.7 s | 0 | 5.9 °/s | 4.0 °/s, peak 5.9 | went on |

"Follow and wait" is the fix without the rewind and the ramp. In the last run the restart
never went faster than the move's own peak and the lag after it stayed at the usual
following lag (0.18°). Each resume logs one `Clamped(Acceleration)`: the limiter closing
the last 0.02° to the path from rest.

The 1 s window for a requested stop (below) was changed after the last robot run, so only
its unit test covers it.

## Late replies

The first three runs (35 000 cycles) have no late cycle. Every later run has them, never
more than `Delay` 2:

| Log | Cycles | `Delay` ≥ 1 | Telegrams missing from the log | Cycle time p99 / max |
| --- | --- | --- | --- | --- |
| `s6_5_1.csv`, `s6_5_2.csv`, `s6_5_3.csv` | 34 995 | 0 | 0 | 4.2 / 4.6 ms |
| `s6_5_4.csv` | 33 514 | 28 | 6 | 4.3 / 10.2 ms |
| `s6_5_1_fix.csv` | 6 153 | 11 | 0 | 4.4 / 8.0 ms |
| `s6_5_3_fix.csv` | 60 683 | 36 | 8 | 4.4 / 9.2 ms |
| `s6_5_rewind.csv` | 8 017 | 6 | 0 | 4.3 / 7.6 ms |
| `end_*.csv`, four logs | 7 473 | 7 | 2 | 4.4 / 10.0 ms |

They sit on a one-second grid. The `IPOC` of the late cycles, modulo 1000 ms, is the same
within a run and moves slowly from run to run: 739 to 751, then 795, 835 to 863, 959 to
967, 15, 31, 47 over 19 minutes. So one source on the Mac side fires about once a second,
on a clock that runs about 16 ms per minute apart from the robot's, and only some of its
firings cost a cycle. It started between the third and the fourth run and went on. Builds
and tests ran on the Mac in that time, but the grid continues through runs with nothing
else running, so they are not it. Not found; the next thing to try is still the real-time
thread class from session 3.

## Open

- A `stop_program()` sent while the program is stopped: the KRL program does not run then,
  so `RSI_OFF` probably waits for Start and the end is reported as `LinkTimeout`. Not tried.
- A pause of several minutes with the enabling switch released (126 s was the longest).
- The start of a session: in `end_watch_cancel.csv` the motor torques are 0 for the first
  60 ms while `ProgStatus` already reads "running". A `move_to` starts too slowly for that
  to matter (0.0001° in 60 ms); a stream that starts at speed in that window would run
  ahead as a resume did. The driver does not wait there.
- The exact pendant texts and KSS numbers of "command velocity A6" and of the operator
  protection message.
- Reconnecting after the pulled cable, S6.3, S6.4, S7 and the 12 ms mode carry over.
