## The A1 stop: T1 speed limit

`J --axis 1 --deg 30 --speed 30 --log runs/s4_a1_v30_b.csv` stopped again, twice, with
`LinkLost(500ms)` on the PC. The pendant showed two messages with the same time stamp:

- `KSS03015 Stop because $SPEED_LIMIT_TEACH_MODE has been exceeded` (originator KS)
- `KSS00489 Stop by $CORRECTION function (reset or block selection required)` (originator A2)

So the controller stopped the robot because the Cartesian speed in T1 went over its teach-mode
limit (250 mm/s); KSS00489 is the consequence. The PC side was clean in every run (`Delay` 0).

| Run | Start A1 | Stopped after | A1 speed, commanded / actual | Tool point radius from A1 | Tool point speed, commanded / actual |
| --- | --- | --- | --- | --- | --- |
| 2026-11-05 `s4_a1_v30.csv` | -77.5° | 0.78 s | 28 / 27 °/s | 333 mm | 163 / 158 mm/s |
| 2026-11-11 `s4_a1_v30_b.csv` (first) | -98.9° | 0.43 s | 15 / 13 °/s | 938 mm | 236 to 245 / 210 to 220 mm/s |
| 2026-11-11 `s4_a1_v30_b.csv` (second, overwrote the first) | -96.5° | 0.43 s | 14 to 15 / 13 °/s | 938 mm | 232 to 245 / 208 mm/s |

Speeds are from the last 8 cycles of each log (the upper value of a range is the last cycle);
the tool point is the `RIst` position in the telegrams. With the arm stretched out the stop
comes as the commanded tool speed reaches about 245 mm/s. The session 2 stop at 163 mm/s was
not read on the pendant; if it was the same message, the controller monitors a point further
from the A1 axis than the reported tool point in that pose (open).

Consequence: in T1 the usable joint speed depends on the pose. Around A1 it is roughly
`250 mm/s / radius`: 15 °/s at 938 mm. Faster moves need T2 or automatic mode.

## Late replies today

Every run of this session has cycles with `Delay` 1, the runs of 2026-11-05 have none:

| Log | Cycles | `Delay` 1 | Telegrams missing from the log | Cycle time p99 / max |

| `s5_py.csv` | 2 753 | 7 | 2 | 4.6 / 8.8 ms |
| `s5_py_stop.csv` | 1 754 | 3 | 0 | 4.4 / 5.9 ms |
| `s5_rust_quiet.csv` (slicer closed) | 2 753 | 8 | 2 | 4.6 / 8.6 ms |

`Delay` never went above 1 (the ETHERNET timeout is 100) and the motion was not affected.

What a late cycle looks like in the log: the telegram is taken about 3.5 ms late and the next
one right after it (cycle times `4.0 7.2 0.5 4.0` ms), or one telegram is skipped
(`4.0 8.6 4.0`). So the driver's thread woke up late; the reply itself took no longer than
usual. Within a run the late cycles cluster at the same phase of the 100 ms client loop.

Closing the slicer changed nothing (`s5_rust_quiet.csv`), so that was not the cause. The likely
one is the scheduling of the driver's thread on macOS: it gets the highest normal priority but
no real-time class (the doctor says so), and the Mac was busier than on 2026-11-05 (load
average 2.8, the window server at about half a core). Not proven. To try: request the
real-time thread class on macOS and repeat S5.

## The 12 ms sensor mode (to try)

RSI has a slower mode: `#IPO`, 12 ms, with the controller filtering the corrections
(`$FILTER`); the program runs `#IPO_FAST`, 4 ms. A 3.5 ms stall is not late in a 12 ms cycle.
The tools take the cycle now (`--cycle-ms 12`), and the driver refuses a session whose
telegrams come at another cycle than it is set to ("cycle mismatch", on the PC and on the
pendant), because every duration and speed limit is counted in cycles.

Not known: whether `RSI_MOVECORR()` with axis corrections runs in `#IPO`. The manual says a
path is corrected only on LIN and CIRC motions in that mode and does not mention sensor-guided
motion (RSI 5.0, p. 49 to 51).

1. On the pendant, in `kuka_rsi.src`: `ret = RSI_ON(#ABSOLUTE)` becomes
   `ret = RSI_ON(#ABSOLUTE, #IPO, #BASE)`.
2. `target/release/rsi-doctor --robot 192.168.10.147 --wait 60 --cycle-ms 12`, start the
   program. Expect 83 telegrams/s. A halt at `RSI_ON` or a message at `RSI_MOVECORR()` answers
   the open question: note the message.
3. `J --cycle-ms 12 --deg 2`, then `J --cycle-ms 12 --axis 1 --deg 30 --speed 10 --log
   runs/s8_a1_12ms.csv`: compare lag and smoothness with the 4 ms run (lag 0.36°).
4. `S --cycle-ms 12 --log runs/s8_stream_12ms.csv`: late replies and `Delay` against today's
   4 ms runs.
5. Once without the flag while the program runs `#IPO`: the PC must refuse with
   "cycle mismatch: the robot sends every 12 ms".
6. Put `RSI_ON(#ABSOLUTE)` back.

The robot's own timeout stays at 100 cycles, which is 1.2 s at 12 ms (0.4 s at 4 ms). The
correction is absolute, so the robot holds the last target meanwhile; the driver's link
timeout follows (1.5 s).
